# Security policy

Hearth holds a household's financial records — account balances, income, bills,
spending. A vulnerability here matters more than the size of the project
suggests, so reports are genuinely welcome.

## Reporting a vulnerability

**Please don't open a public issue.** Use GitHub's private vulnerability
reporting instead:

**[Report a vulnerability](https://github.com/chrislynch97/hearth/security/advisories/new)**
— or go to the repository's **Security** tab → **Report a vulnerability**.

That keeps the details between us until there's a fix, which matters when the
people running the affected version can't patch until one exists.

Useful things to include, in rough order of value:

- What an attacker gets — read another household's data, act as the owner,
  bypass the login gate, and so on.
- The steps to reproduce it, against a demo-mode instance (`npm run demo`) rather
  than anyone's real data.
- The version or commit you tested, and roughly how the instance was deployed
  (LAN, reverse proxy, public).

A rough description is much better than nothing. If you're not sure whether
something counts, report it.

## What to expect

This is a side project maintained by one person, so: no service-level agreement,
and quiet stretches are possible. Realistically you can expect an
acknowledgement within a week, and an honest answer about whether and when it
will be fixed. If something is serious and being actively exploited, say so
prominently and it will jump the queue.

If you'd like credit in the fix or the release notes, say so and you'll get it.

## Scope

**In scope** — anything in this repository: the server, the client, the tRPC API,
the auth and session handling, the Docker image and the shipped compose files.

Particularly interesting, because they're what stands between an exposed instance
and someone else's finances:

- The HTTP gate and the tRPC authorization middleware (`src/server/httpGate.ts`,
  `src/server/trpc/trpc.ts`), including any way to reach a procedure without
  passing both.
- Household scoping — any way one household reads or writes another's rows.
- Sessions, password and MFA handling, invite tokens.
- The startup safety checks that are supposed to stop a misconfigured public
  deployment from booting.

**Out of scope**

- A specific instance's own deployment or configuration. If you've found
  someone's Hearth exposed on the internet, that's a problem with how it was
  deployed, and the right thing is to tell whoever runs it.
- Demo mode's data and credentials. It's deterministic fake data by design.
- Findings that require an attacker to already have the database files or host
  access. The database is not encrypted at rest and this is
  [documented](docs/deployment.md#https--security): two-factor protects the login
  path, not someone who already has the disk.
- Reports generated by a scanner with no explanation of the impact here.

## Supported versions

Fixes land on the latest release. There are no long-term support branches — if
you're running an older version, updating is the fix. The in-app update check
and the [update guide](docs/deployment.md#updating--three-ways) cover how.

## For people running Hearth

The [deployment guide](docs/deployment.md#https--security) has the security notes
for self-hosting. The short version, if your instance is reachable from the
internet:

- Set an owner password and turn on two-factor authentication **before** the
  instance is reachable, not after.
- Set `HEARTH_PUBLIC=1`. Hearth then refuses to boot on the configuration
  mistakes that would expose your data or disarm its own defences, rather than
  starting anyway and warning into a log nobody reads.
- Put TLS in front of it, and set `HEARTH_TRUST_PROXY` to match your actual proxy
  chain — without it, rate limiting and `Secure` cookies both quietly stop
  working.
- Keep backups off-site and encrypted, and restore one at least once. A backup
  you've never restored isn't a backup.
